## Project state

This is a Blast Puzzle (Match-2) game built on Unity's default **2D (URP)** template. The playable core loop — grid, click-to-blast, gravity, refill, score/move win condition — is implemented, plus all three planned power-ups: matching **6-7** blocks creates a **Rocket** (clears its row/column when tapped), **8-9** creates a **Bomb** (clears a 3x3 area when tapped), **10+** creates a **Ball** (clears every block of one color, anywhere on the board, when tapped). Tapping a power-up gathers its whole touching cluster (not just one neighbor) and combines them for a bigger effect: Bomb+Bomb → 5x5, Rocket+Rocket → a cross (same fixed size no matter how many pieces are in the cluster); a Ball combined with a Bomb or Rocket turns every block of the Ball's color into that power-up, each exploding on its own (Bomb wins if both are present); two or more Balls together clear the entire board. Any other power-up caught inside a blast chain-activates too, potentially cascading further. A small preview icon shows on any cell that would create a power-up before it's tapped. Obstacles (Box, Balloon) remain future work. There is no README; this file and `Rules/` are the source of truth.

If the board size ever becomes dynamic per-level at runtime (not just per `LevelData` asset), re-call `Fit` after resizing.

### Architecture (MVC + data-driven + pooled + event-driven)

- `Assets/Scripts/Runtime/` (asmdef `Match2.Runtime`): `Model/` (pure C#: `GridModel` 1D-flattened board + BFS flood fill, `GameStateModel`, `IGridPiece` implementations `ColorBlockPiece`/`RocketPiece`/`BombPiece`/`BallPiece`), `Data/` (ScriptableObjects `BlockTypeData` — now also carries a `TintColor` per color for the Ball — `LevelData`, `BlockPaletteData`, `PowerUpTypeData`), `View/` (`GridView`, `BlockView`, `HudView`), `Controller/` (`GridInputController`, `GameFlowController`), `Systems/Pooling` (`BlockPoolService` wrapping `UnityEngine.Pool.ObjectPool<T>`), `Systems/Events` (`GameEvents`, explicit typed pub/sub), `Systems/Tween` (`IBlockAnimator` seam; `DoTweenBlockAnimator` is the active implementation — eased fall, squash-then-shrink blast, pop-in appear — and `InstantBlockAnimator` remains as a dependency-free fallback/test double, handy for deterministic logic tests since it resolves every animation synchronously).
- **Per-level color count**: `BlockPaletteData` (`Assets/Art/Data/BlockPaletteData_Default.asset`) is a single game-wide asset holding every block color the game can ever use, in a fixed order (currently Blue, Green, Red, Yellow, Pink). `LevelData` no longer lists its own block types directly — it references that shared `palette` plus a `colorCount` int (`[Min(2)]`, defaulting to 5), and its `BlockTypes` property returns the first `colorCount` entries of the palette (clamped to `[2, palette.BlockTypes.Count]` even if `colorCount` is set out of range some other way, e.g. from a script). This is what lets one level use 2 colors and another use 3+ without duplicating `BlockTypeData` references across every `LevelData` asset — to make an easier or harder level, just change `colorCount`, never the palette itself; add a genuinely new color once, to the palette, and every level can opt into it.
- **Power-ups** (Rocket, Bomb, Ball — all three implemented): a power-up piece is an `IGridPiece` that is never `IsMatchable` — `TryBlastAt` treats "tapped piece exists and `!IsMatchable`" as "this is a power-up" (there's no other kind of non-matchable piece yet, so this doubles as the dispatch condition), and always calls `GameFlowController.ActivatePowerUp` (see below — it also covers the lone-power-up and 2-piece-combo cases, there's no separate `ActivateSolo`/`ActivateCombo` split anymore). `GameFlowController.CreatePowerUpForGroup` picks which one a match creates by size (`RocketGroupThreshold = 6`, `BombGroupThreshold = 8`, `BallGroupThreshold = 10` — higher thresholds win when several are met), placed via `GridModel.PlacePiece` and rendered via `GridView.ResolveVisual` + a `PowerUpTypeData` entry in `GridView`'s `powerUpTypes` list (a game-wide constant, not per-level like `LevelData.BlockTypes`). Every activation path funnels into the same shared `GameFlowController.FinishTurnAfterBlastAnimation` (gravity→refill→score→preview refresh) — any future power-up or combo should follow this same pattern rather than duplicating the pipeline. `GridModel.GetLine` (Rocket), `GetArea` (Bomb, and the Bomb+Bomb combo at a bigger radius), `GetCross` (the Rocket+Rocket and Bomb+Ball combos — a plain or thick "+" shape, radius 0 or 1), and `GetAllWithMatchKey` (Ball — scans the *whole* board, not just neighbors, for every matchable cell sharing a `MatchKey`) are the "what does this power-up affect" queries; `GameFlowController.ComputeEffectCells` is the single switch that maps a piece to whichever of these applies, reused by solo activation, the combo fallback, and chain reactions alike. `BallPiece` remembers the `TargetColorId` of the match that created it (this project has no swap/drag interaction, so there's no other way to pick a color at tap time) and `GridView` tints the Ball sprite to `BlockTypeData.TintColor` for that color so the player can see which color it'll clear.
- **Turn re-entrancy guard**: `GameFlowController.isTurnInProgress` blocks `TryBlastAt` from starting a new turn while the current one's animations are still playing (set `true` the instant a tap is accepted, cleared only in `FinishTurnAfterBlastAnimation`'s terminal callback, after the preview refresh). This exists because `GridInputController` has no input-lock of its own — without this guard, a fast double-tap (or tapping mid-animation) could start a second turn while the first is still animating, and a pooled `BlockView` reused by the second turn calls `IBlockAnimator.ResetState` (`DOKill()`) on itself, silently killing whatever tween the first turn's `CallbackBarrier` was still waiting on. Since `DOKill()` never fires the tween's `onComplete`, that barrier's count never reaches zero and its callback — and everything chained after it (gravity, refill, score, preview refresh) — never runs, which is what a player experiences as the board permanently freezing despite still having moves left. Any new async turn path must funnel through `FinishTurnAfterBlastAnimation` exactly once so this flag is reliably cleared; don't add a path that returns early after setting the flag without also clearing it.
- **Power-up clusters and chain reactions**: tapping a power-up gathers its *entire* touching cluster, not just one neighbor — `GameFlowController.FindPowerUpCluster` does a BFS through orthogonally-adjacent non-matchable cells, so e.g. three bombs in a row all combine into one effect from a single tap, the same as two would. `ComputeClusterFootprint` decides that effect via `DetermineClusterEffect`:
  - **Bomb+Bomb** (no Ball, no Rocket) → `WideArea`, a fixed 5x5 centered on the tapped cell.
  - **Rocket+Rocket** (no Ball, no Bomb) → `Cross`, a fixed plain "+" (one row + one column) centered on the tapped cell.
  - **Bomb+Rocket** (no Ball) → `ThickCross`, a fixed 3 rows + 3 columns centered on the tapped cell (`GridModel.GetCross(centerIndex, radius: 1)`) — confirmed by the user ("hem dikey hem yatay da ok ilerler... dikeyde 3 columb... yatayda 3 satır"): both directions fire together, each 3 wide, not just the tapped Rocket's own single-line orientation. Checked before the plain-Bomb/plain-Rocket cases in `DetermineClusterEffect` so a Bomb+Rocket pair never falls into either of those instead.
  - **Ball + Bomb** → `TransformToBomb`, and **Ball + Rocket** (no Bomb) → `TransformToRocket`: handled entirely outside `ComputeClusterFootprint`, by `GameFlowController.ActivateColorTransformCombo` — see the dedicated section below, since this is a multi-step sequenced animation rather than a single instant blast.
  - **Ball + Bomb + Rocket all in one cluster** → `TransformToBomb` — **Bomb takes priority over Rocket** (confirmed by the user: "Bomba önceliklidir Arrowdan"), checked before the Rocket case in `DetermineClusterEffect`.
  - **Ball + Ball** (two or more, no Bomb/Rocket present) → `ClearBoard`: every matchable block on the board blasts via `GridModel.GetAllMatchableIndices()`, regardless of color.
  - Any other mix with no rule above falls back to every cluster member firing its own `ComputeEffectCells` footprint, unioned together (currently unreachable in practice, since every 2-kind, non-Ball combination — Bomb+Bomb, Rocket+Rocket, Bomb+Rocket — now has an explicit rule).

- **Ball color-transform combo sequencing** (`GameFlowController.ActivateColorTransformCombo`): unlike every other combo, this one doesn't blast instantly. The tapped Ball+Bomb/Rocket pair merges and blasts right away (same `PlayMergeBlast` visual as any other combo), then every block sharing the Ball's target color is found (`GetAllWithMatchKey`, read *before* the cluster is blasted — the Ball is gone once blasted, so its `TargetColorId` has to be captured first) and grouped into rows via `GroupByRowTopToBottom` (highest `y` first). `PlayTransformRowsSequentially` then recursively walks the rows top to bottom: for each row, every cell in it visually turns into the target power-up in place (`GridView.PlayColorToPowerUpTransform` → `BlockView.PlayTransformInto` → `IBlockAnimator.PlayTransform`, a punch-scale pulse — no new piece is ever actually placed in the `GridModel`, only the sprite changes), then that row's cells blast using their power-up's own effect (`ComputeEffectCellsForKind` — a Bomb's 3x3 `GetArea` or a Rocket's `GetLine`), which still runs through `ExpandWithChainReactions` so a real power-up caught in a row's splash still chain-fires. Only once a row's blast animation finishes does the next row start; `FinishTurnAfterBlastAnimation` runs once, after the last row, with the summed score from every row plus the initial cluster.
  For same-kind clusters (Bomb+Bomb, Rocket+Rocket), the effect size stays fixed **regardless of how many pieces are in the cluster** (confirmed by the user: "Her zaman 2'li kombinasyonla aynı boyut kalsın" — always stay the same size as the 2-piece combo) — three bombs together still make one 5x5, not a bigger one. Every cluster member is folded into the cleared set even if the effect footprint doesn't geometrically reach it, so nothing in the tapped cluster ever survives its own combo. On top of that, `ExpandWithChainReactions` grows the final blast in place: any power-up caught inside the affected cells that wasn't already part of the initial cluster chain-activates too — its own `ComputeEffectCells` footprint gets folded in, which can catch further power-ups, and so on (verified live: a bomb's blast revealing a rocket revealing a ball two hops away, all three going off in the same tap). Chain-triggered power-ups blast in place; only the initially-tapped cluster gets the merge-slide visual (see below).
- **Merge-into-place visuals**: whenever multiple cells are consumed to create or trigger something at one specific cell, the "extra" cells visually slide into that cell first and only blast once they arrive, rather than each just vanishing where it stood. `GridView.PlayMergeBlast(centerIndex, mergingIndices, clearedIndices, onComplete)` is the one method for this: everything in `mergingIndices` slides to `centerIndex` (`BlockView.PlayMergeSlide`, reusing `IBlockAnimator.PlayMove`'s fall-style ease) via a `CallbackBarrier`, and once they've all arrived, every cell in `clearedIndices` blasts together — movers blast individually (already detached from `viewsByIndex`), everything else blasts in place through `GridView.BlastIndices` (extracted from `PlayBlast` so both share the same per-cell blast+release logic). Two call sites use it: (1) a match big enough to create a power-up — `mergingIndices` is every other matched block, so the whole group appears to converge into the new power-up; (2) `GameFlowController.ActivatePowerUp` — `mergingIndices` is every *other* member of the tapped power-up cluster (see above), so the whole cluster visually merges into the tapped cell while any collateral cells caught in the effect (ordinary blocks, or chain-activated power-ups elsewhere on the board) blast in place like normal. The Model already clears every affected cell as part of the same `Blast` call regardless of how the View animates it, so vacated cells refill through the ordinary `ApplyGravity`/`Refill` pass — no special-casing needed there. `GameFlowController.ContinueTurnAfterBlast` (plain `PlayBlast`, no merge) and the two `PlayMergeBlast` call sites all end by calling the shared `FinishTurnAfterBlastAnimation` (gravity→refill→score→preview refresh), extracted so the differing lead-in animation never requires duplicating that tail.

It had no good filled/tintable circle for Ball (its `target_round_*`/`dot_*` icons are thin outlines, not solid fill), so Ball uses `PlaceholderSpriteGenerator`'s procedural shiny-orb icon (`Match2/Generate Ball Placeholder Sprite` menu, `Assets/Art/Sprites/Generated/BallPlaceholder.png`) instead — a neutral grey body + white highlight, deliberately left uncolored so `SpriteRenderer.color` tinting works. That generator (`Assets/Scripts/Editor/PlaceholderSpriteGenerator.cs`) is the general last-resort fallback for when neither Kenney pack has a fitting shape; import new cursor-pack icons as `Sprite`/`Single` mode with `spritePixelsPerUnit` = their native size (e.g. 64).
- **Power-up previews**: the board recomputes, every time it settles (initial deal + after every completed turn — never per-tap), which cells are currently "one tap away" from creating a power-up, and shows a small semi-transparent overlay icon on those cells so the player can see it before tapping. `GridModel.ComputeGroupSizes()` does one full-board BFS sweep (sharing its flood-fill core with `FindConnectedGroup`) and returns every matchable cell's group size in one pass — far cheaper than calling `FindConnectedGroup` per cell. `GameFlowController.RefreshPowerUpPreviews()` maps those sizes through the same threshold logic as real creation (`DeterminePowerUpKind`, extracted so creation and preview can't drift apart) and calls `GridView.ShowPowerUpPreviews`, which sets each `BlockView`'s second, dedicated `previewRenderer` (a child `SpriteRenderer` on `Block.prefab`, added above the main one in sorting order, ~55% scale, ~0.85 alpha) to the matching `PowerUpTypeData` sprite, or hides it. Call `RefreshPowerUpPreviews()` after `GameBootstrapper` shows the initial board, and it's already wired into the end of `ContinueTurnAfterBlast`'s pipeline for every subsequent turn — no other call site should be needed.

- **Flying score popups**: every time a cell blasts, anywhere in the game (normal match, solo power-up, any combo, chain reaction, or a color-transform combo's row), a "+10" `ScorePopupView` (world-space `TextMeshPro`, `Assets/Prefabs/ScorePopup.prefab`) pops in at that cell's position and flies toward the HUD's `ScoreText`, then destroys itself — purely cosmetic, the actual score already changed in the model at that point. Kept as its own class rather than folded into `LevelWinView` since the two outcomes share no behavior (one is a multi-step animated sequence plus a progress advance, the other is an instant unconditional return) — don't merge them just because both react to a game-over-style event.

Sfx` menu items) synthesizes short WAV clips procedurally (sine tones/sweeps with an exponential-decay envelope, written as raw PCM16 WAV bytes — no external audio library needed) into `Assets/Audio/Generated/`: `Blast.wav`, `PowerUp.wav` (generated but not currently wired to anything — there's no dedicated "power-up activated" `GameEvent` distinct from a normal match, so nothing consumes it yet), `LevelWon.wav`, `LevelLost.wav`. `Systems/Audio/SfxController` (Game scene only) is a thin `GameEvents` listener — same role as `HudView` but for sound instead of text — that calls `AudioSource.PlayOneShot` for `OnScoreChanged` (every blast, any cause), `OnLevelWon`, and `OnLevelLost`. Caught and regression-tested (`PopulateInitialBoard_WithBoxes_IncludesThemInTheSpawnList`) — any future piece placed directly via `PlacePiece` outside of `Refill` needs this same "also add it to the spawn list" treatment. Rendered via a dedicated `GridView.boxSprite` field (not a `PowerUpTypeData` entry, since there's only one obstacle kind so far); the placeholder art is `PlaceholderSpriteGenerator.GenerateBoxSprite` (`Match2/Generate Box Placeholder Sprite` menu) — a bordered crate with an X-plank pattern and corner rivets. `LevelData_02`/`_03` use `InitialBoxCount` 4/8 respectively as part of the difficulty curve; a Balloon or any further obstacle should follow this exact pattern (new `IGridPiece`, excluded from `IsPowerUp`, its own sprite field or data asset, placed at level start only) rather than introducing a new mechanism.

## Golden rules for writing code here

`Rules/` contains two ebooks that are the binding style/quality standard for all C# written in this project: Unity's *Create a C# Style Guide* (*Writing Cleaner Code That Scales*) and *Dive Into Refactoring* by Alexander Shvets (Refactoring.Guru). Apply the rules below whenever writing or editing code; when they don't cover a case, default to whichever choice keeps the code simplest and most consistent with itself.

### Naming and casing
- Identifiers begin with a letter or `_`; avoid special/Unicode characters.
- Pascal case for classes, interfaces, methods, enums, namespaces, and public members. Interfaces get an `I` prefix (e.g. `IKillable`).
- Camel case for local variables and parameters, and for private fields (optionally prefixed with `_`, e.g. `_currentHealth`) — pick one convention and use it everywhere.
- Booleans are prefixed with a verb that reads as a question (`isDead`, `hasDamageMultiplier`), and boolean-returning methods are phrased as a question (`IsGameOver`, `HasStartedTurn`).
- Methods start with a verb (`GetDirection`, `FindTarget`); variables are nouns. Don't abbreviate except for loop counters or math; make names searchable and pronounceable.
- Don't repeat the class name in its own members (in a `Player` class, use `Score` not `PlayerScore`). No jokes/puns in names — they won't read well after the tenth reading.
- Enum names are singular Pascal-case nouns, except `[Flags]` bitwise enums, which are pluralized.
- Events use a verb phrase for before/after state (`OpeningDoor` / `DoorOpened`); the method that raises one is prefixed `On` (`OnDoorOpened`); prefer `System.Action`/`Action<T>` over hand-rolled delegates.

### Formatting
- Allman brace style (opening brace on its own line); always use braces, even for single-line and nested single-statement blocks.
- One variable declaration per line. Single space around operators, after commas, before flow-control parentheses; no space between a method name and its parentheses, and no padding spaces inside brackets/parentheses.
- Keep lines reasonably short (roughly 80–120 chars) and prefer real formatting over column-alignment tricks.
- Use expression-bodied properties (`public int MaxHealth => maxHealth;`) for single-line read-only properties; use `{ get; set; }`/explicit accessors otherwise, and mark setters private when write access shouldn't be public.
- Expose Inspector fields via `[SerializeField] private` rather than making a field `public` just to see it in the Inspector; use `[Range(min, max)]` and `[Tooltip("...")]` where they add value; group related exposed values into a `[Serializable]` struct/class instead of a long flat field list.

### Classes and methods — keep everything small
- A class should do one thing (single-responsibility principle) — when a `Player`/`Paddle`/`Board`-style class starts handling input, movement, data, and audio/FX all at once, split it into cooperating classes (e.g. `PaddleInput`, `PaddleMovement`, `PaddleData`, `PaddleAudio`) rather than growing one god class.
- One `MonoBehaviour` per file, and the file name matches the class name.
- Organize each class top-down like a newspaper article: high-level/public methods first, followed by the private helpers they call — don't make a reader hunt for implementation details before the big picture.
- Within a class, group members in this order: fields, properties, events/delegates, Unity lifecycle methods (`Awake`, `Start`, `OnEnable`, `OnDisable`, `OnDestroy`, ...), public methods, private methods.
- Methods should be short (a good rule of thumb: if it's pushing past ~10 lines or you feel the urge to comment a section of it, extract that section into its own well-named method).
- Prefer fewer method parameters; group related parameters that travel together into their own type instead of a long parameter list (3-4+ params is a smell). Avoid boolean "mode" flags — write two clearly-named methods instead of one method branching on a flag.
- Avoid side effects: a method should do what its name says and nothing else outside its own scope.
- Don't duplicate logic (DRY) — duplicated files/text are fine, duplicated *logic* is not; extract the shared behavior into one method/class so a fix only has to happen once.

### Comments
- Prefer a better name over a comment. Most code shouldn't need comments if it's simply and clearly named.
- Comments should explain *why*, not *what* — non-obvious decisions, tricky logic, workarounds. Don't restate what the code already says.
- Use `[Tooltip("...")]` instead of a comment for serialized Inspector fields, and `///` XML summaries for public API methods where useful.
- Don't leave commented-out code, dev-diary-style notes, or attribution comments (`// added by X`) — rely on git history for that. Keep `TODO`s current and delete them once done or no longer relevant.

### Code smells to watch for and fix (from *Dive Into Refactoring*)
Treat these as warning signs during and after writing code — when spotted, refactor before moving on:
- **Bloaters** (grow over time until unwieldy): Long Method, Large Class, Primitive Obsession (using raw primitives/strings instead of small dedicated types), Long Parameter List, Data Clumps (the same group of variables/parameters showing up together repeatedly — promote them to their own type).
- **Object-Orientation Abusers** (OO applied incompletely/incorrectly): large `switch`/`if-else` chains that should be polymorphism, Temporary Fields (fields only meaningful during one algorithm), Refused Bequest (a subclass that doesn't want most of what it inherits — favor composition or restructure the hierarchy), Alternative Classes with Different Interfaces (duplicate concepts, inconsistent interfaces — unify them).
- **Change Preventers** (one conceptual change forces edits in many places): Divergent Change (one class changes for many unrelated reasons — split it), Shotgun Surgery (one change requires many small edits across many classes — consolidate related behavior), Parallel Inheritance Hierarchies.
- **Dispensables** (things that shouldn't exist): unnecessary Comments, Duplicate Code, Lazy Class (not doing enough to justify existing — inline or merge it), Data Class (only fields and getters/setters, no behavior — move behavior in), Dead Code (delete it, don't comment it out), Speculative Generality (YAGNI violations — abstractions built for a future that hasn't arrived).
- **Couplers** (excessive coupling between classes): Feature Envy (a method more interested in another class's data than its own — move it there), Inappropriate Intimacy (classes reaching into each other's internals), Message Chains (`a.GetB().GetC().GetD()` — hide the chain behind a method), Middle Man (a class that only delegates to another — remove it and call the real thing directly).

### General principles
- KISS and YAGNI: prefer the simplest solution that solves the problem at hand; don't build for hypothetical future requirements, and use Unity's built-in solutions before writing custom ones.
- Understand *why* something is broken before patching around the symptom.
- Refactor when it will genuinely help readability or maintainability — not compulsively, and not as a substitute for shipping working code.
- Favor small, incremental commits/changes with tests run in between over large speculative rewrites.

## Working in this repo

- There are no build/lint scripts — Unity projects are built and run through the Unity Editor (or `Unity -batchmode` CLI for automation), and there is no CI configured in this repo.
- Tests live in `Assets/Scripts/Tests/EditMode/` (`Match2.Tests.EditMode` asmdef) and run via Unity Test Runner (Window > General > Test Runner), or in batchmode with `-runTests -testPlatform EditMode`. Keep new gameplay-rule logic in the `Model/` layer (pure C#, no `MonoBehaviour`) so it stays unit-testable without the Editor's Play mode.
- `Library/`, `Temp/`, `Logs/`, and `UserSettings/` are Unity-generated local caches — do not hand-edit or commit meaningful work there.
- Follow the existing `Assets/Scripts/Runtime/{Model,View,Controller,Data,Systems,Utils}` layering for new gameplay systems (e.g. obstacles) rather than introducing a new structure.
- **Editor Play button starts whichever scene is currently open**, not necessarily `MainMenu` — if `Game.unity` happens to be the open/active scene when you press Play, that's where it starts, which looks like "the game doesn't start from the main menu" but isn't a bug. `EditorSceneManager.playModeStartScene` can be set to `MainMenu.unity` to force Play to always boot there regardless of which scene is open; this is a **per-user Editor preference, not project data** (not stored in anything under `ProjectSettings/`, so it doesn't survive a fresh clone or `git` history and has to be re-set locally). A real device/standalone build is unaffected either way — it always starts at Build Settings' scene 0, which is `MainMenu.unity`.
